JSON Schema Draft 2020-12 is the canonical machine-readable format.

## 2. Versioning rules

- `schemaVersion` is required in every payload and uses a stable value such as `case-public.v2`.
- Adding an optional field may remain within `v1` only when old consumers continue to behave correctly.
- Removing a field, changing meaning, changing an enum, or making an optional field required creates a new major contract version.
- Stored attempts retain the contract and rubric version used when they were created.
- Public Decision Card snapshots retain their publication schema version.
- A migration may create a new projection, but it must not rewrite the historical original response.

## 3. Identifier and time rules

- IDs are opaque, globally unique strings generated by the server.
- Public slugs are random and must not encode user IDs, email addresses, case IDs, or timestamps.
- Timestamps use ISO 8601 UTC strings.
- The server owns `createdAt`, `committedAt`, `completedAt`, and `publishedAt`.
- Client-provided timestamps are display hints only and never establish workflow order.

## 4. Field classification

### Safe before commitment

- Case ID
- Estimated duration
- Decision type
- Scenario
- Known evidence statements
- Constraints
- Prompts and choices

### Reveal only after commitment

- Company and product identity
- Source title and canonical URL
- Real launch outcome
- Reference trade-offs
- Evidence commentary that could disclose the source

### Always private

- Stable authenticated user ID
- Email
- Draft responses
- Raw original and revision history unless explicitly selected for publication
- Evaluator model details and operational errors
- Private Skill Map observations
- Idempotency keys

### Explicitly public by publication

- Public card slug
- Display name chosen for the card
- Case title and decision type
- User-approved decision, reasoning, assumptions, and revision summary
- Source provenance
- Publication time

## 5. Projection rule

Public and pre-commit payloads are built by constructing new allowlisted objects. They must not be produced by serializing an internal record and deleting selected keys.

Required projections:

```text
Internal case → case-public.v2
Internal case + committed ownership → case-reveal.v2
Completed attempt + user-approved fields → private proof preview
Private proof preview + explicit publish action → decision-card-public.v1 snapshot
```

This rule prevents newly added private database fields from leaking into existing public responses.

## 6. Attempt invariants

- `draft` may contain mutable draft responses.
- `committed` requires `committedAt` and a complete immutable `originalResponses` array.
- `feedback_ready` requires one valid `evaluation.v1` record.
- `revised` requires either revision responses or a non-empty keep-original rationale.
- `completed` requires a valid evaluation and the revision requirement.
- `evaluation_failed` is ineligible for Skill Map updates and publication.
- Public card state does not change attempt completion state.

## 6A. Candidate pool invariants

- AI HOT item IDs are unique per owner in `candidate_product_pool`.
- Only selected `ai-products` items that pass the current practice-fit gate may be inserted as `queued`.
- Repeated syncs may update source metadata and fit labels but must not reset `generating`, `active`, `completed`, or `rejected` lifecycle states.
- Random case generation atomically claims only a `queued` item.
- A generated item becomes `completed` only when its owned attempt reaches completed revision status.
- `completed` and `rejected` items are never eligible for random selection.

## 7. Evidence invariants

- Every case evidence item has a unique `evidenceId` within the case.
- Every evaluation citation must reference an evidence ID from the evaluated case.
- A factual feedback claim without supporting case evidence must use status `insufficient_evidence` and contain no invented citation.
- A cited evidence item may support a fact or interpretation but the evaluation must label which one it is.
- Source URLs appear only in reveal and public-card contracts.

## 8. Idempotency and replay

- State-changing endpoints require an idempotency key scoped to user, operation, and target record.
- Replaying a successful key returns the original result without creating another commit, evaluation, revision, or card.
- Reusing a key with a different body is rejected.
- Idempotency records are private operational data and never appear in a public contract.

## 9. Validation order

For every write:

1. authenticate the user;
2. validate the request contract;
3. load the record with owner scope;
4. validate the current state transition;
5. validate referenced case, prompt, choice, and evidence IDs;
6. perform the mutation atomically;
7. construct an allowlisted response projection; and
8. emit a metadata-only audit event.

For model output, schema validation occurs before state mutation, followed by evidence-ID validation and semantic fail-closed checks.

## 10. Contract-specific notes

### `case-public.v2`

This contract intentionally has `additionalProperties: false`. Prohibited reveal fields cannot be added without a contract change and an explicit review.
Each evidence item carries an analytical `category` and a provenance label: `shipped_fact`, `company_reported`, or `inference`. The contract also includes target dimension, difficulty, and core prompt identity.

### `case-reveal.v2`

This contract may be returned only after committed ownership is verified. It contains provenance and what the company chose or shipped, but no later market-performance tracking.

### `attempt.v1`

This is a private workflow view. `originalResponses` become immutable at commitment. `revisionResponses` are distinct and optional until revision.

### `evaluation.v1`

The service accepts only `valid` evaluations for feedback and skill updates. Invalid model output is represented operationally rather than coerced into a valid envelope.

### `decision-card-public.v1`

This is a standalone snapshot. The public route reads it without joining private attempt, user, evaluation, or Skill Map tables.

## 11. Step 2 contract acceptance checks

- Every registry entry has a valid JSON Schema file.
- Every schema rejects unspecified top-level properties.
- The pre-commit schema has no company, source, real-outcome, or reference-answer property.
- The public card schema has no owner ID, email, private note, evaluator model, or raw hidden-case property.
- Attempt status and required timestamps are internally consistent at service validation time.
- Evaluation ratings and dimensions are bounded enums.
- Evidence citations are arrays of explicit IDs rather than free-form source claims.
- All JSON schema files parse successfully before Step 2 approval.
